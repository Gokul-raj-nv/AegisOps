# INC-1521 — Payment Service DB Pool Exhaustion

**Date:** 2024-08-14
**Duration:** 47 minutes
**Severity:** P1
**Service:** payment-service
**Status:** Resolved

## Summary

Payment service experienced a 100% HTTP 500 error rate for 47 minutes due to database connection pool exhaustion. The issue was triggered by a spike in flash sale traffic that saturated the 20-connection pool.

## Timeline

| Time | Event |
|---|---|
| 14:02 UTC | Flash sale campaign started |
| 14:08 UTC | DB connection utilization reached 95% |
| 14:11 UTC | First `QueuePool limit` errors in logs |
| 14:13 UTC | Alert fired: payment-service error rate >15% |
| 14:15 UTC | On-call engineer paged |
| 14:22 UTC | Root cause identified: pool exhaustion |
| 14:31 UTC | `DB_POOL_SIZE` increased from 20 to 50, rolling restart initiated |
| 14:38 UTC | Service recovered, error rate dropped to <1% |
| 14:49 UTC | All-clear declared |

## Root Cause

Database connection pool size (`DB_POOL_SIZE=20`) was insufficient for the traffic volume during the flash sale. Each payment request holds a DB connection for ~800ms (including Stripe API wait), so at >25 concurrent requests, the pool exhausted.

## Contributing Factors

1. No alerting at 80% pool utilization (only at 15% error rate)
2. Flash sale traffic not communicated to platform team
3. `max_overflow=0` means no buffer

## Resolution

- Increased `DB_POOL_SIZE` from 20 to 50
- Rolling restart of payment-service

## Action Items

- [x] Add 80% pool utilization alert
- [x] Add 95% pool utilization critical alert
- [ ] Evaluate PgBouncer for connection multiplexing
- [ ] Pre-scale payment-service before planned campaigns

## Impact

- ~1,400 failed payment attempts
- ~$85,000 in lost revenue (estimated)
- 0 data loss or corruption
