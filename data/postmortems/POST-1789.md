# Postmortem: INC-1789 — Redis OOM / Notification Loss

**Date:** 2024-10-25
**Author:** Notifications Team
**Severity:** P2 | Duration: 2h 15m

## What Happened

A consumer bug caused notification-service to crash repeatedly. The Redis queue grew unchecked until Redis hit its memory limit. With `allkeys-lru` eviction policy, Redis silently dropped queue items — resulting in ~8,400 missed order confirmation notifications.

## Key Failure

The system had no visibility into queue depth. Redis memory usage was not monitored. The consumer crash was not alerted on. The only signal was user reports 90 minutes into the outage.

## Action Items

| Item | Owner | Status |
|---|---|---|
| Monitor Redis memory usage | Notifications | Done |
| Alert on queue depth > 10,000 | Notifications | Done |
| Switch to `noeviction` policy | Notifications | Done |
| Implement dead-letter queue | Notifications | In Progress |
| Add consumer crash alerting | Notifications | Done |

## Lessons Learned

- Silent failures (data loss without error) are worse than noisy failures.
- Queue-based systems must monitor queue depth, not just consumer health.
- `allkeys-lru` is dangerous for workloads where every message matters.
