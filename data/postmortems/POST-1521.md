# Postmortem: INC-1521 — Payment DB Pool Exhaustion

**Date:** 2024-08-16
**Author:** Platform Engineering
**Severity:** P1 | Duration: 47 minutes

## What Happened

On 2024-08-14, the ShopFlow payment service became completely unavailable for 47 minutes due to database connection pool exhaustion. This was caused by flash sale traffic exceeding the pool capacity of 20 connections.

## Contributing Factors

1. **Insufficient pool size:** `DB_POOL_SIZE=20` with `max_overflow=0` provides no buffer.
2. **No early warning:** Alerts only fired at 15% HTTP error rate, not at 80% pool utilization.
3. **Communication gap:** Campaign team did not inform platform team of expected traffic spike.
4. **Slow Stripe calls:** Each payment holds a DB connection while waiting for Stripe (~800ms), reducing effective throughput.

## Five Whys

1. Why did payment-service return 500 errors? → DB connections unavailable
2. Why were DB connections unavailable? → Pool exhausted
3. Why was pool exhausted? → Traffic spike exceeded pool size
4. Why did pool size not scale? → Static config, no auto-scaling
5. Why was there no early warning? → Alert threshold set too high

## Lessons Learned

- Alert on leading indicators (pool utilization) not lagging indicators (error rate).
- Connection hold time directly limits throughput — minimize DB connection hold time.
- Campaign traffic must be communicated cross-team in advance.
